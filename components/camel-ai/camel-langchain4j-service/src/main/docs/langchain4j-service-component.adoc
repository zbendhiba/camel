The LangChain4j Service component invokes user-defined https://docs.langchain4j.dev/tutorials/ai-services[LangChain4j AI Services] from Camel routes. You define the AI Service interface, build it with the LangChain4j `AiServices` builder, and register it in the Camel registry. The component looks it up and invokes it. LangChain4j owns all AI behavior: prompts, memory, tools, guardrails, and agentic loops.

The component does not create or configure AI Services. It performs registry lookup and method invocation only.

== Why not the bean component?

The `xref:components::bean-component.adoc[bean]` component can also invoke a registered object. This component adds AI-specific behavior on top:

* Parameter binding follows LangChain4j annotations. The body binds to the `@UserMessage` parameter. Headers bind to `@V` template variables and the `@MemoryId` parameter.
* Fail-fast validation at route startup. Missing services, ambiguous methods, and invalid method names fail before the first message flows.
* A stable, component-scoped header namespace for AI concerns such as memory IDs and template variables.

== URI format

[source]
----
langchain4j-service:serviceName[?method=methodName]
----

Where *serviceName* is the name of the AI Service bean in the Camel registry.

The `method` parameter is optional when the AI Service interface has a single business method. It is required when the interface has multiple business methods. Method overloading is not supported: method names must be unique.

== Parameter binding

The producer binds AI Service method parameters from the exchange:

[width="100%",cols="30%,70%",options="header"]
|===
| Parameter annotation | Bound from

| `@UserMessage` | The message body, converted to the parameter type.
| `@V("variableName")` | The header `CamelLangChain4jService<VariableName>`. The first letter of the variable name is uppercased. For example `@V("context")` binds from `CamelLangChain4jServiceContext`.
| `@MemoryId` | The header `CamelLangChain4jServiceMemoryId`.
| _none (single parameter)_ | The message body.
|===

Rules:

* A method with multiple parameters must annotate every parameter with `@UserMessage`, `@V`, or `@MemoryId`.
* At most one parameter can be annotated with `@UserMessage`.
* `@V` and `@MemoryId` headers are required at runtime. A missing header fails the exchange.
* Zero-parameter methods are supported. Use a method-level `@UserMessage("...")` template. The message body is ignored.
* A non-void return value becomes the new message body. A void method leaves the body unchanged.

== Usage

=== Single-method AI Service

Define the interface, build the service, and register it:

[source,java]
----
interface Assistant {
    String chat(@UserMessage String text);
}

Assistant assistant = AiServices.builder(Assistant.class)
        .chatModel(model)
        .build();

camelContext.getRegistry().bind("assistant", assistant);
----

Invoke it from a route:

[source,java]
----
from("direct:chat")
    .to("langchain4j-service:assistant");
----

The body is passed as the user message. The AI response becomes the new body.

=== Multi-method AI Service

When the interface has more than one method, select one with the `method` parameter:

[source,java]
----
interface Assistant {
    String chat(@UserMessage String text);
    String summarize(@UserMessage String text);
}

from("direct:summarize")
    .to("langchain4j-service:assistant?method=summarize");
----

Omitting `method` on a multi-method interface fails at route startup.

=== Template variables from headers

LangChain4j prompt templates use `@V` variables. Each variable binds from a header:

[source,java]
----
interface Assistant {
    @SystemMessage("Use the following context when answering: {{context}}")
    String analyze(@UserMessage String text, @V("context") String context);
}

from("direct:analyze")
    .setHeader("CamelLangChain4jServiceContext", constant("background info"))
    .to("langchain4j-service:assistant");
----

=== Memory ID for stateful AI Services

AI Services with chat memory take a `@MemoryId` parameter. It binds from the `CamelLangChain4jServiceMemoryId` header:

[source,java]
----
interface Assistant {
    String chat(@UserMessage String text, @MemoryId String memoryId);
}

Assistant assistant = AiServices.builder(Assistant.class)
        .chatModel(model)
        .chatMemoryProvider(memoryId -> MessageWindowChatMemory.withMaxMessages(10))
        .build();

from("direct:chat")
    .setHeader("CamelLangChain4jServiceMemoryId", header("sessionId"))
    .to("langchain4j-service:assistant");
----

Each distinct memory ID keeps its own conversation history.

=== Tool-enabled and agentic AI Services

The component invokes plain, tool-enabled, and agentic interfaces the same way. LangChain4j executes all agentic behavior, such as tool calling and reasoning loops, inside the invocation. The final result is returned to the route:

[source,java]
----
Assistant assistant = AiServices.builder(Assistant.class)
        .chatModel(model)
        .tools(new WeatherTools())
        .build();

from("direct:agentic")
    .to("langchain4j-service:assistant");
----

=== Quarkus

In Quarkus JVM mode, register the AI Service in the Camel registry as a named bean:

[source,java]
----
@Produces
@Named("assistant")
Assistant assistant(ChatModel model) {
    return AiServices.builder(Assistant.class)
            .chatModel(model)
            .build();
}
----

Known limitation: CDI client proxies, such as AI Services created by the Quarkus LangChain4j extension with `@RegisterAiService`, expose container interfaces in addition to the business interface. Interface resolution then fails fast at route startup with a `multiple business interfaces` error. Register a service built directly with `AiServices.builder(...)` instead. Full Quarkus CDI proxy support is deferred work.

== Error handling

Startup failures. These fail route startup, before any message flows:

* The service name is not found in the registry.
* The service does not implement a resolvable business interface, or implements several.
* The interface has multiple methods and no `method` parameter is set.
* The `method` parameter names a method that does not exist.
* The method name is overloaded.
* Parameter binding is ambiguous, such as multiple `@UserMessage` parameters or un-annotated parameters on a multi-parameter method.

Exchange failures. These fail the exchange and route to the Camel error handler:

* The body is null but a user message parameter is expected.
* A required `@V` or `@MemoryId` header is missing.
* The AI Service method throws. The original exception is unwrapped from the reflection layer and propagated as the exchange exception, so `onException` clauses match the real type:

[source,java]
----
onException(dev.langchain4j.exception.ModelNotFoundException.class)
    .handled(true)
    .setBody(constant("The model is not available"));
----

== Observability

The component relies on default Camel endpoint spans. The span of the `to` step carries the endpoint URI, which includes the service name and the method. The component adds no custom tracing in this version.

Model-level GenAI telemetry, such as token usage and model latency, is the responsibility of LangChain4j and its observability integrations.
